PHASE 3: Parse the ground truth

For example:

The empty list means the S1 entity is a singleton.

Convert it internally into pair-level labels:

PHASE 4: Build the validation framework FIRST

This is essential.

We don't want to make a model and discover after submitting that our local evaluation is wrong.

4.1 Split by Source 1 entity

For example:

80% S1 → training
20% S1 → validation

The split should be at the S1 level rather than randomly splitting pair rows.

4.2 Implement competition metric

Create:

src/evaluate.py

Implement:

$$ F_{0.5} = \frac{1.25PR} {0.25P+R} $$

But importantly, this is a macro F₀.₅ across Source 1 entities, not simply one global pair-level F₀.₅.

For every S1:

true matches
predicted matches
precision
recall
F0.5

Then:

macro_F0.5 = mean(F0.5 across S1)
PHASE 5: Explicit singleton evaluation

The official challenge explicitly emphasizes this behavior.

Therefore our evaluator should separately report:

PHASE 10: Build blocking

This is the first major ML component.

Create:

src/blocking.py

The challenge says blocking uses a cheap key involving name and address, with records entering the same block through similar names or shared addresses.

The Acme example is especially important.

For:

S1:
Acme Robotics Inc.
500 Market St, San Jose

the candidate block contains:

S2-118820
Acme Robotics Inc.
500 Market Street, San Jose

S2-540221
Acme Robotix
12 Elm Rd, San Jose

S3-905477
Acme Robotics
Nr City Hall, San Jose

S3-063118
Acme Bakery
500 Market St, San Jose

The first and third are likely true matches.

The second and fourth are look-alikes.

All four enter blocking.

The matching model later removes the two false candidates.

PHASE 11: Implement multiple blocking keys

Don't rely on a single blocking rule.

Block A: Exact normalized name
name_normalized

Example:

acme robotics inc
Block B: Name without legal suffix
name_without_suffix

So:

Acme Robotics Inc.
Acme Robotics Incorporated

can enter the same block.

Block C: Name tokens

Use informative tokens from:

Acme Robotics

such as:

acme
robotics
Block D: Name prefix / character key

For typo robustness:

name_normalized[:4]
name_normalized[:5]

or character n-gram keys.

Block E: Address tokens

For:

500 Market Street San Jose

use tokens such as:

500
market
san
jose
Block F: Numeric address key

Use:

house_number

and other useful numeric components.

This allows the S3 "Acme Bakery" look-alike in the official example to enter the Acme candidate set because the address is shared.

Block G: Name + address key

Construct a combined cheap key such as:

name_prefix + address_token

This is closer to the blocking concept explicitly shown in the PPT.

PHASE 12: Union the blocking strategies

This is extremely important.

We should do:

name_candidates
        UNION
address_candidates
        UNION
name_address_candidates
        UNION
token_candidates
        UNION
numeric_candidates

rather than requiring every condition simultaneously.

Conceptually:

                   S1
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
     NAME        ADDRESS      COMBINED
     BLOCK        BLOCK         BLOCK
       │            │            │
       └────────────┼────────────┘
                    ▼
                  UNION
                    │
                    ▼
             Candidate pairs

Why?

Because blocking is supposed to favor recall. Amazon explicitly says that the block intentionally pulls in look-alikes.

PHASE 13: Measure blocking recall

This is the most important blocking metric.

For validation:

Total true pairs

versus:

True pairs present in candidate set

Calculate:

$$ BlockingRecall = \frac{\text{True pairs inside candidate set}} {\text{Total true pairs}} $$

For example:

10,000 true matches
9,850 retrieved by blocking

Blocking recall = 98.5%
Rule:

If blocking recall is poor:

DO NOT improve the matching model yet.

Fix blocking first.

Amazon explicitly says blocking sets the recall ceiling.

PHASE 14: Control candidate explosion

There is a trade-off.

If a token like:

"the"

appears in 100,000 records, using it as a block produces a disaster.

Therefore:

if block_size > MAX_BLOCK_SIZE:
    don't use that key

or use more specific keys.

For example:

bad:
common_token

better:
common_token + address_token

We want:

HIGH BLOCKING RECALL
+
LOW CANDIDATE VOLUME

The three stages we should optimize in order

1. Blocking recall

Did we find the true match among the candidates?

2. Matching precision

Can the model remove the look-alikes?

3. Macro F₀.₅

Does the complete S1-level prediction perform well under the actual competition metric?

That ordering follows the challenge's own explanation: blocking determines the recall ceiling, the matching model filters candidates, and the final submission is evaluated using precision-weighted macro F₀.₅.

One final principle: we should not start coding the sophisticated matcher until we have actually measured blocking recall on the training validation split. If the correct pair never enters the block, no amount of model wizardry can resurrect it. That's the central engineering constraint of this challenge.
