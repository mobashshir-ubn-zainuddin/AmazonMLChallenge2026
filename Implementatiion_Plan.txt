Amazon ML Challenge — Current Implementation & Achievements

At the current stage, the business entity resolution pipeline has completed the preprocessing, exploratory analysis, ground-truth analysis, blocking-strategy development, blocking implementation, and blocking-recall evaluation stages.

The most important achievement so far is that the current blocking system recovers approximately 98% of the known true S1→S2/S3 matches on the training ground truth, before any machine-learning/fuzzy matching model is applied.

1. Problem Understanding

The challenge is a business entity resolution / record linkage problem.

The dataset contains three sources:

Source 1 (S1) — canonical/reference business records
Source 2 (S2) — noisy business records
Source 3 (S3) — another noisy business source

The task is to determine which S2/S3 records correspond to each S1 business.

A key characteristic of the challenge is that an S1 entity can have:

no matching entity
exactly one matching entity
multiple matching entities

Therefore, this is not simply a one-to-one classification problem.

The final output must contain:

source1_entity_id    matched_entity_ids

with potentially multiple matched IDs for a single S1.

There is also a required candidate-pair file:

source1_entity_id    candidate_entity_ids

The candidate set must contain the final matches.

4. Preprocessing Pipeline

A dedicated preprocessing module was implemented.

The preprocessing is designed to normalize records while remaining Unicode-safe.

The normalization includes:

Unicode normalization

Unicode normalization uses NFKC.

This helps standardize equivalent Unicode representations.

Case normalization

Text is converted using Unicode-aware case folding rather than simple ASCII-only lowercasing.

Whitespace normalization

Repeated whitespace is normalized.

Business-name normalization

Business names are cleaned while preserving Unicode letters and numbers.

Special symbols are normalized, including:

& → and
@ → at

Punctuation is removed appropriately.

Legal suffix handling

Business legal suffixes are identified and removable.

Examples include:

Inc
Incorporated
Ltd
Limited
LLC
Corp
Corporation
Co
Company
PLC
Pvt
SARL
SA
SAS
EURL
SC
SNC

This produces:

name_no_legal_suffix

in addition to the normal cleaned name.

Address preprocessing

Addresses are normalized separately.

The preprocessing extracts:

address_numbers
address_tokens
address_sorted_tokens

These later become useful for blocking.

Country normalization

Country values are normalized.

For example:

United States
USA

are normalized to:

us

Importantly, the pipeline does not hard-code the entire system to only the countries present in training.

This matters because the test set introduces France.

8. Why Blocking Was Implemented

The raw scale makes exhaustive pairwise matching infeasible.

There are millions of records in S2 and S3.

Therefore, the system uses:

S1 record
   ↓
Blocking
   ↓
Small candidate set
   ↓
Detailed matching

rather than:

S1 record
   ↓
Compare against millions of S2/S3 records

The purpose of blocking is not to make the final entity-resolution decision.

Its purpose is:

Remove obviously irrelevant records while retaining as many true matches as possible.

This distinction is important.

9. Blocking Architecture

A dedicated blocking.py module was implemented.

It currently contains 12 blocking strategies.

They are divided into three groups.

9.1 Name-based blocking
1. name_exact

Uses:

country + name_clean

Conceptually:

us|amazon
2. name_no_suffix_exact

Uses:

country + name_no_legal_suffix

This handles differences such as:

ABC Corporation
ABC Corp
ABC

where legal suffixes should not prevent a match.

3. name_sorted_exact

Uses the sorted name-token representation.

This helps with token-order variation.

For example, conceptually:

ABC Global Services

versus:

Global Services ABC

can share the same sorted-token representation.

4. name_prefix4

Uses:

country + first 4 characters of name_no_legal_suffix

This is intentionally broader than exact matching.

It provides substantial recall for noisy names.

5. name_token

Uses the longest meaningful token from the normalized name.

The exact helper logic is:

split into tokens
remove duplicates for selection
prioritize longest token
tokens of length ≥4 are preferred
deterministic lexical ordering is used when lengths are equal

This logic is implemented centrally in _longest_token().

10. Address-Based Blocking

Three independent address strategies are implemented.

6. address_exact

Uses:

country + address_clean

This captures records where the normalized address is identical.

7. address_numbers

Uses:

country + address_numbers

This captures records that may have significantly different address text but share the extracted address numbers.

This turns out to be particularly useful.

8. address_token

Uses the longest meaningful address token.

This provides a broader address-based blocking route.

11. Composite Blocking

Four combined name/address strategies were implemented.

9. name_address_exact

Uses:

country
+
name_clean
+
address_clean
10. name_no_suffix_address

Uses:

country
+
name_no_legal_suffix
+
address_clean
11. name_no_suffix_address_numbers

Uses:

country
+
name_no_legal_suffix
+
address_numbers
12. name_prefix4_address_number

Uses:

country
+
first four characters of name_no_legal_suffix
+
first address number

These composite strategies provide additional routes for records where both name and address contain useful information.

12. Missing-Value Handling Was Corrected

An important blocking issue was identified and fixed.

Previously, a missing address could theoretically produce:

us|

instead of an invalid/empty blocking key.

Similarly, partially missing composite fields could produce keys such as:

us|company|

Those are undesirable because many records could accidentally enter the same block.

The implementation was corrected so that a blocking key is only valid when all fields required by that strategy are non-empty.

For example:

(country + "|" + address).where(
    country.ne("") & address.ne(""),
    ""
)

Therefore:

country = us
address = ""

produces:

""

rather than:

"us|"

For composite keys, every required component must be populated.

This is particularly important because the dataset contains a substantial number of missing addresses.

13. Consistency Between Blocking and Recall Evaluation

A separate blocking_recall.py was implemented to evaluate the blocking strategies against the known training ground truth.

A critical design requirement was established:

blocking.py and blocking_recall.py must produce exactly the same blocking key for the same record and strategy.

The recall evaluator therefore reconstructs the keys from the processed TSVs rather than relying on pre-generated block columns.

It also uses the same:

_longest_token()

and:

_first_address_number()

helpers.

This avoids evaluating one implementation while eventually using a different implementation.

14. Memory-Aware Recall Evaluation

The dataset is too large to construct a complete S1 × S2/S3 pair table.

Therefore, blocking_recall.py evaluates the known ground-truth pairs directly.

It loads only the relevant blocking key for each strategy.

For example:

name_exact

loads only the columns necessary for that strategy.

The evaluation is therefore much more memory-conscious than constructing all possible candidate pairs.

STEP 16 — Handle Class Imbalance

There will likely be far more negative candidate pairs than positive pairs.

Therefore, inspect:

Do not simply train on an enormous negative set without checking its composition.

STEP 17 — Split Training Data Correctly

Avoid leakage.

The same S1 entity can have multiple true matches.

Therefore, train/validation splitting should be performed at the S1 entity level, not randomly at the individual pair level.

For example:

S1 entities
   ├── training S1 entities
   └── validation S1 entities

Then all pairs associated with an S1 remain in the same split.

This prevents information from the same S1 entity appearing in both train and validation.

. The biggest issue: UNION index construction

The per-strategy analysis is good.

This part:

followed by:

counts = s1_keys.map(target_strategy_counts[strategy]).fillna(0).astype(int)

is a good approach.

It computes:

block key → number of records

rather than materializing candidate pairs.

That is exactly what we want for the individual strategy statistics.

But the UNION is different

For UNION, the script does:

idx = {}

for eid, key in zip(target_df.index, keys_series):
    if key != "":
        if key not in idx:
            idx[key] = []
        idx[key].append(eid)

and does this for all 12 strategies.

Then for every one of the 2.2 million S1 records, it creates a Python set:

candidates = set()

and inserts every candidate ID from all 12 strategies.

Why this matters

Claude described this as memory-efficient, but this is only partially true.

It avoids a Cartesian product, which is excellent.

However, Python:

dict
  → list
      → millions of Python strings

for 12 indexes can consume a very large amount of RAM.

Then it additionally constructs a set() for every S1.

Your previous miss-analysis process reached roughly 26 GB private memory, so I would not casually run this UNION implementation without considering the machine's available RAM.
